# Civora: connected plan from verified product to pilot, customers and investors

Prepared October 13, 2026. This sequences the founder-approved focused P1–P6 plan under the master roadmap; it does not replace their authority or mark any unfinished milestone complete. Planning only: this document does not authorize deployment, purchases, paid generation, outreach or production-data experiments.

## Shared product contract

Remain web-first and reuse the existing backend, Mapbox, accounts, sharing and subscriptions. First support one parcel with a small office/retail project, a primary building, one or two accesses, surface parking, entered constraints and preliminary supported calculations/quantities. Sourced conceptual costs stay unknown when evidence is unavailable. Outputs are preliminary, not construction approval.

The canonical project is the geometry/input authority. Direct controls, chat and alternative selection use governed transactions against that authority. One transaction must feed history, save state and affected-system freshness together. Calculations bind to their input revision; late/stale results stay history, not active truth. Brief/source changes invalidate relevant previews and results. View-only sharing stays view-only across all paths.

Exports identify which saved revision and representation they use. Drawing-only exports exclude calculations; calculated packages cannot label stale outputs current. Both retain units, source, assumption, limitation and ownership checks. Billing never overrides permissions, engineering status, verification or export safety.

## One continuing proof project

Use a repository-owned synthetic commercial project for repeatable software regression, then a separate rights-cleared real-site project for professional/workflow acceptance. Keep project identity, source manifest, canonical revision, edit history, calculation input identity, export manifest and release identity connected. Synthetic evidence never becomes real-site validation by relabeling it.

Exercise this chain at each relevant gate:

Create/open -> import/site brief -> draw/generate -> direct edit -> supported chat edit -> compare/Apply alternative -> review conflicts/unknowns -> confirm affected calculations -> quantities/pricing -> save/reopen -> PDF/DXF -> external CAD continuation.

Also exercise Undo/Redo, copy/replace/cancel in a second tab, permissions, locked geometry, offline/save failure, late calculation and changed-source cases. Test affected behavior after each change; run broader regressions and the complete browser workflow at major milestone exits. Record failures, skips and environment limits separately.

## Steps and dependencies

### 1. Fix the pilot offer and acceptance contract

Depends on: existing focused plan and founder choices.

- Confirm initial customer, city/county, project envelope, supported calculations, browser policy and explicit exclusions.
- Define what a successful customer deliverable looks like and how time/corrections will be measured.
- List dependencies requiring founder access, files, reviewer authorization or policy approval. Missing source values remain unknown.

Output: one short supported-scope/acceptance checklist used by engineering, onboarding, terms, sales and the demo.

Done when: the customer promise and measurable exit checks are agreed, without unsupported compliance or capacity claims.

### 2. Establish the exact source and test baseline

Depends on: Step 1 scope; can begin while real-site inputs are being obtained.

- Identify intended changes in the inherited dirty working tree; preserve unrelated edits and avoid blanket commits.
- Establish a scoped candidate/checkpoint and inventory. Retain failing probes and known limitations.
- Confirm reproducible dependencies and distinguish development advisories from production findings.
- Assign an evidence record to each supported feature: implemented, tested locally, hosted-tested, externally accepted or open.

Output: identifiable candidate plus a coverage/gap list; no assumption that the previous passing checkpoint proves later changes.

Done when: the intended candidate and its dependencies are reviewable and reproducible. Final release identity is re-established after later changes.

### 3. Close cross-feature state and trust gaps

Depends on: Steps 1–2.

- Audit direct editing, chat, alternatives and legacy controls against the canonical transaction boundary.
- Verify brief/source protection, explicit overrides, units, zero/blank/invalid inputs and permissions across those paths.
- Verify save acceptance, history, Undo/Redo, two-tab branches, locked objects, deletion and group dependencies.
- Bind calculations/previews to live inputs and confirm selective recalculation and late-result rejection.

Output: shared regression probes proving these modules agree on the same project state.

Done when: no critical state, trust, permission or data-loss failure remains in the supported workflow. Do not rebuild functioning features merely to rename their architecture.

### 4. Complete the supported commercial design loop

Depends on: Step 3; real-source acquisition can run in parallel.

- Execute the continuing proof project on the actual website without hidden operator intervention.
- Connect geometry alternative selection to supported calculations, conflict review, quantities and sourced conceptual cost data.
- Verify entered supported constraints; disclose recorded-only or unsupported requirements.
- Include direct and equivalent supported chat edits, infeasible alternatives, selective rerun, save and reopening.

Output: repeatable end-to-end evidence and a limitations matrix shared with exports, onboarding and sales.

Done when: the entire supported loop passes with matched canonical data; geometry checks are not represented as full engineering feasibility.

### 5. Make the export package internally consistent

Depends on: Step 4 and its representation/limitations matrix.

- Match project revision, declared units, geometry and disclosures across PDF, DXF and JSON/manifest.
- Test building/road/access/parking details actually claimed by each export path; disclose missing stall/aisle/profile detailing.
- Test stale/unknown-unit/corrupt-geometry/ownership failures, not only successful downloads.
- Render and inspect PDF pages and parse DXF entities/coordinates/layers. Verify claimed visual/3D modes; exclude unverified paid imagery from the initial promise.

Output: preliminary package suitable for external review, with precise scope and source records.

Done when: internal artifact checks pass. External reusable-CAD acceptance still belongs to Step 8.

### 6. Establish performance, reliability and supported limits

Depends on: Steps 4–5 for realistic workloads; profiling may begin earlier.

- Measure representative pilot inputs and concurrent jobs; define supported file/object/project/run limits.
- Improve expensive recomputation with output equivalence, candidate isolation and conflict/rollback tests.
- Verify asynchronous progress, timeout, retries, worker restart and stale/incomplete result handling.
- Complete accessibility and supported-browser checks; fix the Firefox environment or obtain an explicit supported-browser decision.

Output: tested operating envelope and truthful failure behavior, reused by quotas, onboarding, support and the paid offer.

Done when: supported workloads meet agreed expectations and recover safely. One timing sample is not capacity certification.

### 7. Verify and release the actual hosted candidate

Depends on: Steps 2–6 and founder approval for the specific deployment.

- Finalize a clean scoped checkpoint after the fixes; run full backend and relevant browser/build/dependency checks against it.
- Verify hosted account/tenant isolation, sharing, uploads, worker recovery and artifact durability with authorized test data.
- Restore backups into an isolated recovery destination, never over customer data; document rollback and incident ownership.
- Present changes, test evidence, limits, target and rollback plan for deployment approval.
- After approval, deploy on existing infrastructure and repeat critical authenticated website checks; confirm live release identity or roll back.

Output: identifiable, recoverable live candidate with hosted evidence.

Done when: the tested release is actually live and hosted gates pass. Health 200 alone is insufficient.

### 8. Obtain real-site engineering, CAD and workflow acceptance

Depends on: Steps 1, 5 and 7. Reviewer/source arrangements can begin earlier with authorization.

- Obtain rights-cleared survey/parcel/constraint inputs and qualified licensed-engineer/CAD reviewers.
- Have them review calculations independently and open exports in the intended CAD version.
- Record discrepancies, geometry/unit checks, editable continuation and actual cleanup/redrawing required.
- Have a qualified designer complete the workflow; repair findings and rerun affected checks.
- Any material software/input change invalidates affected acceptance evidence and requires re-review.

Output: attributable acceptance for exact software, inputs, deliverables and preliminary-use scope.

Done when: professional and CAD/workflow findings support the agreed pilot scope. No seal, municipal approval or construction acceptance is implied.

### 9. Prepare customer operations and verify existing billing

Depends on: Step 1 scope and Step 6 limits. Drafting and sandbox billing checks can run alongside engineering; customer activation requires Steps 7–8 and accepted policies.

- Confirm onboarding, support contact/coverage, incident response, access pause/removal and project exit/export paths.
- Approve customer terms, privacy/confidential-data handling, retention/deletion and any applicable business requirements with appropriate human review.
- Reuse subscriptions/payment infrastructure. Test plan entitlements, payment/webhook behavior, retries/duplicates, failure, renewal, cancellation and refund/invoice/receipt paths that the offer promises.
- Record pricing, trial/pilot/conversion rules, acceptance and billing owner. Test that billing cannot bypass engineering truth or tenant boundaries.

Output: a supported pilot offer and verified activation/support/payment checklist.

Done when: the selected free or paid pilot can be operated responsibly; billing presence alone is not acceptance. Public self-service expansion is not required for the first controlled pilot.

### 10. Run one pilot, fix findings, then expand

Depends on: Steps 7–9; explicit authorization before inviting or sharing files.

- Start with one firm and a defined project/use scope.
- Measure baseline versus Civora completion time, manual corrections, export cleanup, failures, support effort and return usage.
- Repair critical issues before expansion; preserve reproducible regression tests from pilot findings.
- Verify willingness to pay/renew, not just positive comments.
- Expand toward the master target of 3–5 firms and at least 10 real studies; measure the target 50% time savings, usable CAD handoff, no critical trust/data loss and at least two firms willing to keep paying.

Output: customer evidence, prioritized fixes and a permissioned case study; no invented traction.

Done when: the initial firm accepts the supported workflow and subsequent expansion is supported by evidence. A controlled paid pilot may begin after the payment gates, before all larger traction targets are met.

### 11. Build investor readiness alongside customer evidence

Depends on: Step 1 for positioning; Steps 4–10 progressively strengthen proof. Investor conversations do not require finishing every master phase or guarantee funding.

- Prepare the demo, deck, one-page overview, customer/competition narrative and honest limitations.
- Add verified pilot metrics, return usage, willingness to pay, costs and authorized customer evidence as obtained.
- Prepare financial assumptions, funding ask, milestone-based use of funds, hiring/technical plans and risks.
- Verify company/ownership/IP and financial diligence materials with appropriate human support. Status remains unknown until inspected.

Output: a coherent investor package whose product claims, metrics and funding milestones match the actual release and customer evidence.

Done when: the package is accurate and diligence-ready; no funding outcome is promised. Early relationship-building can occur in parallel with authorization.

## Roles and advancement rules

Software agent: inspect, implement scoped fixes, test, prepare artifacts/checklists and report evidence. Founder: decide market/scope/pricing/policies, arrange legitimate inputs/access/reviewers/partner, authorize spend/deployment/outreach and accept business tradeoffs. Qualified humans: independently review engineering/CAD results and applicable legal/business matters.

For every step, report what changed, why, what passed, what failed or remains unverified, the dependent steps affected and the next gate. No percentages of readiness without a defensible measured basis. Passing local tests cannot close hosted or human gates.

A critical safety/data issue pauses affected customer use, not merely the next feature. A later change must trigger the relevant downstream tests and review: state -> calculations -> exports -> release -> professional acceptance -> customer promise. Preserve a clean interface with concise normal controls; detailed limitations belong in the relevant review/source/export/onboarding context.

## Starting point

Scope is provisionally the existing single-parcel office/retail pilot. Immediate software work is baseline/checkpoint review and remaining cross-feature/calculation/performance gates. Founder inputs needed to close real-site gates: target jurisdiction, rights-cleared site files, authorized engineer/CAD reviewers and the first partner. Existing infrastructure remains the default; no new purchase is assumed.
