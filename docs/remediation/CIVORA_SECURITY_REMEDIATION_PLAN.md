# CIVORA SECURITY REMEDIATION PLAN

Baseline: 2026-10-15, ab7db888e85fb9b6125551ecff769d08e0ca7322. **PROPOSED; no exploitation, network probing, production access, dependency installs/scans or security changes performed.**
Owners: application security lead, platform/DB lead, privacy counsel; independent reviewer must not merely approve their own patches. Full task contracts/efforts/alternatives/rollback are in the backlog.

## 1. Threat boundaries and release policy

Untrusted browser/user text/files/GIS/PDF content → API identity → project/organization authorization → canonical writes/jobs → outbound providers/storage → artifacts/reports → external recipients. Build/dependency/CI identities and operator diagnostics form separate privileged boundaries. AI output is untrusted proposed input, not a role, source attestation or calculation approval.

Attacker models: unauthenticated bot; ordinary invited account; compromised browser/session; malicious collaborator; hostile provider/upload; compromised dependency/build; internal operator error. Tenant access checked server-side on every source, project, job, download, export, queue and async execution. CORS is not authorization. Session hashing does not protect XSS or a compromised runtime; CSP does not replace escaping/permission checks.

Beta blockers: reachable High/Critical exposures, identity misbinding, unguarded design writes, material source-loss risk, or sensitive-data collection without approved consent. Public gate adds reviewed browser/proxy/supply-chain and operator protections. Disabled feature can satisfy a scoped exclusion only with enforceable route/config restriction, negative tests and approved disclosure. No live penetration test implied.

## 3. Identity/session migration sequence

1. Decide address ownership and browser transport policy, privileged roles and threat model.
2. Add schema/session metadata in approved isolated migration tests, with old readers able to ignore additive fields.
3. Introduce digest-based issue/lookup and expiry; never print session values. Handle old opaque tokens via one-way exchange inside explicitly bounded window, or revoke with clear sign-in flow.
4. Re-authenticate pending email/unverified member access through operator proof or verification token. Owner/project memberships stay recorded but not automatically trusted solely from old email.
5. Verify active tabs/mobile/multi-device, logout, password/account disable and all-session revoke; job authorization rechecked at execution and publication.
6. Retire raw-token lookup after cutoff; purge old raw values according to approved backup/retention/security policy.
7. Any rollback incompatible with newer sessions forces safe reauthentication/roll-forward. Do not restore raw, never-expiring credentials to make a rollback easy.

Invitation and verification tokens: cryptographic random entropy, hashed persistence, purpose/user/org/project binding, expiry, single-use atomic consumption, revoked status and redacted audit. Generic responses prevent enumeration. Operator provisioning must record who verified what and when; support can never “prove identity” by knowing a public email.

## 4. Egress and file handling detail

DNS checks alone are insufficient if a client re-resolves later; use validated resolution/connected-peer control or enforce network-layer destinations. HTTP proxy/environment behavior must not bypass policy. Every redirect and resolved address evaluated; do not follow unknown redirected schemes. Backend URL allowlisting must not trust frontend filtering. Custom internal GIS endpoints require separate operator-controlled deployment policy and cannot be supplied by ordinary user.

Uploads: enforce limits before commit, stream hashing, authenticate owner, no cross-tenant dedup-existence oracle; preserve original name as metadata only. Large raster/PDF/point-cloud parsers require CPU/memory/page/point/decompression caps and cancellation. These additional parser risks are planned verification, not newly proven vulnerabilities. Safe download types/sandbox/nosniff and no script execution from uploaded content. Preserve source hashes through imports, derived models and exports.

## 5. Collection/privacy/control-plane checks

Operational telemetry is purpose-limited; engineering learning is separate consent. No raw passwords/tokens/customer prompts or geometries in public reports. Redaction tested with synthetic sentinels. Data export/deletion includes learning logs/datasets and references under approved retention, with legal-hold and backup-retention exceptions explained. IP/source rights can forbid training even where user consents. Org policy must constrain user consent.

Detailed diagnostics/support operations require dedicated operator role, auditable access and least-privilege project access. “Admin” in project UI is not automatic system operator. Secret handling includes environment access policy, CI logs/artifacts, public bundles and Git history scanner; no production secrets read in this plan.

## 6. Supply chain, external review and closure

Authorized execution later must record tool/advisory DB timestamp, lockfile/image digest, dependency scope/count/skips, exploitability path and suppressions. Inspect Python and Node runtime/dev/test tools, OS images, GIS native libraries, model artifacts and CI actions. Dependency pinning is not safety without update/review procedures. Do not apply blanket npm audit --force or downgrade major framework config to silence scans.

Independent security reviewer evaluates code/isolated exploit simulations, authorization matrix (user/project/org/operator), tenant/source/job/artifact boundaries, negative egress/auth tests, browser/session protections, migration/restore and consent. Production penetration testing requires separate targets/method/time approval. No current live exploitation is planned here.

Closure record: original SEC/CAN ID → root cause → approved design → fix revision → negative/positive tests → current candidate identity → independent reviewer and residual impact → B/C decision. Findings can be “contained by disabled feature,” never “fixed” solely by not testing it. Exceptions require named owner, compensating controls, expiry and reviewer; no exception to knowingly wrong supported engineering outputs or known cross-tenant access.
